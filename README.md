# Wills Matter Dashboard

An internal web app for working through Wills / estate-planning matters at a
Victorian law practice: a dashboard of matters, a structured checklist per matter,
progress tracking and a "What needs my attention?" view.

> **Prototype — fictional/test data only.**
> This is a local prototype. It is **not** approved for confidential client
> information. See [Before using with real client data](#before-using-with-real-client-data).
>
> Checklist items are workflow prompts, **not legal advice**, and do not replace
> the firm's precedents, procedures or supervision.

---

## Running it locally

You need **Node.js 20 or later** and **pnpm**.
Check with `node -v` and `pnpm -v`. If pnpm is missing, run `npm install -g pnpm`.

All commands are run from the project folder.

```bash
cd "/path/to/CRM-DASHBOARD"

pnpm install        # 1. install dependencies (first time, or after pulling changes)
pnpm db:setup       # 2. create the local database and load fictional sample matters
pnpm dev            # 3. start the app
```

Then open **http://localhost:3000** in your browser. Stop the app with `Ctrl + C`.

| Command | What it does |
|---|---|
| `pnpm dev` | Start the app in development mode (auto-reloads on code changes) |
| `pnpm db:setup` | Create/upgrade the database, seed the checklist template and load sample matters (safe to re-run) |
| `pnpm db:reset` | **Delete** the local database and start again with fresh sample data |
| `pnpm test` | Run the automated tests (uses a temporary in-memory database) |
| `pnpm typecheck` | Check TypeScript types |
| `pnpm build` then `pnpm start` | Production build and run |

The database is a single file at `data/wills.db`. It is excluded from git.

## What's in Phase 1

- **Dashboard.** Headline counts (active, requiring attention, overdue), matters by
  stage, a "Requiring attention" list, and a matter table with search, status filter,
  attention filter and sort. Click any matter to open it.
- **New matter / edit matter.** Client, matter, Will and family details. Only the client
  name and matter number are required. A matter number is suggested automatically.
- **Matter workspace.** Header with client, matter number, status (changeable inline) and
  progress. Tabs: Overview, Instructions, Estate, Will checklist, Drafting, Execution,
  Tasks, Dates, Notes, Documents.
  - **Overview** opens with **What needs my attention?** (overdue and due-soon next
    action, approaching or passed execution date, next checklist items) and a
    **Continue** button that jumps to the next incomplete item.
  - **Checklist.** 7 stages and 95 items. Tick or untick, add a note to any item,
    rename, remove, add custom items (such as extra assets). Completion records who and when.
  - Progress = completed checklist items ÷ total items, overall and per stage.
- **Checklist template** (`Checklist template` in the sidebar). Edit, add, reorder or
  remove the firm template without touching code. Changes apply to **new** matters only.
- **Activity log.** Key events per matter (created, status changes, items completed).

Tasks, key dates, timestamped notes and fuller filtering come in Phase 2. The document
register comes in Phase 3.

## Architecture

| Layer | Choice |
|---|---|
| App | Next.js (App Router) + React + TypeScript |
| Database | SQLite (single local file) via Drizzle ORM |
| Validation | Zod, on the server for every write |
| Styling | Tailwind CSS, small in-house components, system fonts |
| Tests | Vitest (unit + integration against in-memory SQLite) |

```
src/
  app/                    Pages (routes) and server actions
    actions.ts            The ONLY entry points that change data (validate → service → refresh)
    page.tsx              Dashboard
    matters/new/          New matter form
    matters/[id]/         Matter workspace (layout = header + tabs; [section] = tab pages)
    settings/checklist/   Checklist template editor
  components/             UI components (ui/, dashboard/, matter/, checklist/, template/)
  lib/                    Pure logic shared by UI/server: domain lists, dates, progress,
                          attention rules, validation
  server/
    db/schema.ts          Database tables
    db/client.ts          Connection + automatic migrations
    services/             All database reads/writes (matters, checklist, template, dashboard)
    seed/                 Default checklist template + fictional sample matters
    current-user.ts       Placeholder "who is using the app" (replace with real auth)
drizzle/                  SQL migration files (generated by `pnpm db:generate`)
scripts/setup-db.ts       db:setup / db:reset
```

Key decisions:

1. **The checklist is data, not code.** The template lives in the database and is copied
   onto each matter when it is created, so editing the template never silently changes an
   existing matter. `src/server/seed/default-template.ts` is only used to seed an empty
   database.
2. **One service layer.** Pages and actions never query the database directly. Auth,
   permissions and audit logging can be added in one place. Services are `async` so
   moving to PostgreSQL won't change their callers.
3. **Clients and matters are separate tables**, so a client can later have several
   matters (for example Powers of Attorney) and the app can grow into general matter management.
4. **Change attribution.** Rows record `updatedBy` and an activity log is written for key
   events. This is the foundation for a proper audit log.
5. **Dates** are stored as `YYYY-MM-DD`. "Today" and overdue calculations use Melbourne time.

Changing the database schema: edit `src/server/db/schema.ts`, run `pnpm db:generate`,
and commit the new file in `drizzle/`. Migrations apply automatically on startup.

## Security and privacy

- **No third-party data transmission.** No external APIs, analytics, AI services, cloud
  storage, CDNs or web fonts. The app only talks to its own local server.
- **No secrets in code.** Optional settings go in `.env.local` (see `.env.example`), which
  git ignores. So are the `data/` folder and all `*.db` files.
- All writes are validated server-side. Search engines are told not to index pages.

### Before using with real client data

This prototype is **not** production-ready. At minimum, the following would be needed,
together with the firm's IT and risk and compliance sign-off:

- **Authentication** (e.g. firm SSO / Microsoft Entra ID) and **per-user permissions**.
  Currently anyone who can open the app can see and change everything, and changes are
  attributed to `APP_USER_NAME`.
- **Hosting on firm-controlled infrastructure** with HTTPS. `pnpm dev` is for local use only.
- **Encryption at rest** for the database and backups (SQLite files are not encrypted).
- **Backups and recovery** that are tested, plus retention and destruction policies.
- **A tamper-evident audit log** (the current activity log is not tamper-proof).
- **Multi-user database** (e.g. PostgreSQL) instead of a single local file.
- **Security review** (dependency scanning, penetration test) and a **privacy assessment**
  against the firm's obligations.
- Integration with the firm's **document management system** rather than storing documents here.
